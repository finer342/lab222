## 1. Баг із `this` у `ship.fire` та способи його виправлення

У класі `Ship` метод `fire(world)` оголошений як звичайний метод прототипу (`Ship.prototype.fire`). Усередині нього ми звертаємося до властивостей екземпляра через `this`: `this.alive`, `this.fireTimer`, `this.pos`, `this.angle`, `this.vel`.

### Що станеться при наївній передачі в слухач подій:
```js
// ПОМИЛКА: передаємо посилання на метод без об'єкта-власника
window.addEventListener('keydown', ship.fire);
```
Згідно з **чотирма правилами визначення `this`** у JavaScript:
1. **Default binding (виклик за замовчуванням):** коли функція викликається без об'єкта перед крапкою (як це робить браузер усередині `addEventListener`), у `strict mode` (а всі ES-модулі автоматично працюють у `strict mode`) `this` дорівнює `undefined` (або `window` у нестрогому режимі).
2. **Implicit binding (неявна прив'язка):** працює лише в момент виклику `ship.fire(world)`, коли `ship` стоїть зліва від крапки. При передачі `ship.fire` як колбеку посилання на об'єкт губиться.
3. **Explicit binding (явна прив'язка):** `call`, `apply`, `bind` примусово фіксують `this`.
4. **New binding:** при виклику через `new` створюється новий об'єкт і стає `this`.

У результаті натискання клавіші призведе до помилки:
`TypeError: Cannot read properties of undefined (reading 'alive')`.

### Як це виправити (фікс і альтернативи):
1. **Стрілкова функція-обгортка (використано в `src/main.js`):** стрілкові функції не мають власного `this`, тому замикають змінну `world` із зовнішньої області видимості, а виклик `world.ship?.fire(world)` зберігає неявну прив'язку (`Implicit binding`):
   ```js
   window.addEventListener('keydown', (event) => {
     if (event.code === 'Space') {
       world.ship?.fire(world);
     }
   });
   ```
2. **Явна прив'язка через `.bind()` (`Explicit binding`):**
   ```js
   const boundFire = ship.fire.bind(ship, world);
   window.addEventListener('keydown', boundFire);
   ```
3. **Стрілкове поле класу (альтернатива на рівні `Ship`):**
   ```js
   class Ship extends Entity {
     fire = (world) => { /* this завжди вказує на екземпляр Ship */ };
   }
   ```
   *Мінус цього підходу:* функція створюється заново для кожного екземпляра `Ship`, замість того щоб один раз лежати в `Ship.prototype`.

## 2. Чому композиція замість глибокої ієрархії класів

За умовою в проєкті використано лише **один рівень спадкування** (`class Ship extends Entity`), а дві наскрізні фічі — **самонаведення (`homing`)** та **бонус на карті (`pickup`)** — реалізовано через **композицію функцій поведінки** (`entity.addBehavior(fn)`).

### Як виглядала б глибока ієрархія спадкування (антипатерн):
Якби ми будували все через `extends`, довелося б розділяти сутності за ознакою «рухається / стоїть» та «має самонаведення / не має»:

```text
Entity
 ├── StaticEntity
 │    └── Pickup
 └── MovableEntity
      ├── Ship
      ├── Bullet
      │    └── HomingBullet
      └── Asteroid
           └── HomingAsteroid
```

**Проблеми такого дерева класів:**
1. **Дублювання коду та «проблема ромба»:** логіка самонаведення (`homing`) потрібна і для `HomingBullet`, і для `HomingAsteroid`. В односпадковому JavaScript не можна успадкувати одночасно `Bullet` і `HomingMixin` без складних міксинів — доводиться копіювати код пошуку цілі й повороту вектора швидкості у два різні класи.
2. **Комбінаторний вибух класів:** якщо завтра з'явиться вибуховий астероїд або астероїд, що залишає бонус після знищення, доведеться створювати `ExplosiveHomingAsteroid`, `LootableAsteroid` тощо.
3. **Неможливість змінити поведінку в рантаймі:** об'єкт, створений як `new Bullet()`, не може стати самонавідним під час польоту без перестворення екземпляра.

### Переваги обраного підходу (1 рівень `extends` + композиція):
* `Ship extends Entity` інкапсулює лише специфічний стан гравця (`#hp`, кут повороту, перезарядку та метод `fire()`).
* `createHomingBehavior({ targetKind, turnRate, speed })` — чиста фабрика поведінки, яка однаково підключається через `entity.addBehavior(...)` до кулі (ціль `'asteroid'`) і до мисливського астероїда (ціль `'ship'`).
* `Pickup` — це звичайний `Entity` з нульовою швидкістю, радіусом колізії та підключеним `createPickupBehavior()`, що без жодних додаткових підкласів бере участь у спільному циклі `World.step()` та системі коло-коло колізій.
